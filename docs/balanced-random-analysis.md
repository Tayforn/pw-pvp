## 1. Що це за проєкт

**Стек.** React 19 + Vite 5 + TypeScript (strict), без UI-бібліотек і без роутера (власний History-API роутер у `src/app/useRoute.ts`: `/`, `/tournaments`, `/register?t=<id>`, `/rules`, `/admin`, `/series/:slug`, `/t/:id`). Бекенд — Supabase (Postgres + RLS + Auth + Realtime + pg_cron), один проєкт спільно з pw-events. Деплой — GitHub Pages через `.github/workflows/deploy.yml` (base `/pw-pvp/`, `dist/404.html` = копія `index.html` для History-роутингу). Стилі — один `styles.css` (~560 рядків) з токенами теми і словником класів `.card`, `.field`, `.field-row`, `.checkbox-row`, `.badge.good|warn|bad|mute`, `.hint`, `.btn.btn-primary|btn-ghost|btn-bad|btn-sm`, `.modal*`. Тестів і typecheck-кроку в CI немає (`package.json`: лише `dev`/`build`/`preview`).

**Сутності (схема `supabase/migrations/0001…0016`).**

| Таблиця | Що зберігає | Важливе для фічі |
|---|---|---|
| `tournament_series` | серії; одна активна (0013), `auto_weekday` → cron раз на 2 год створює наступний турнір (0012, 0014) | автостворення копіює **фіксований список** колонок: `bracket_type, team_size, rules_md, prizes_md, third_place_match` (0012:30–51); `bracket_new_look` уже губиться |

| `bracket_matches` | сітка: `participant1_id`, `participant2_id`, `winner_id` — усі **FK → `registrations(id)`** `on delete set null`; `bracket_side` winners/losers/final/third_place; `score` | учасник сітки = рядок `registrations`; `BracketView.nameFor` показує лише `nickname` |
| `admins` | `role` superadmin / gm | ГМ бачить лише свої турніри; RPC-патерн `security definer` + перевірка ролі (0007) |

**Потоки.** Адмін створює турнір → гравці подають заявки (анонімно; клієнт додатково блокує другу заявку з того самого браузера через localStorage) → адмін підтверджує/відхиляє у `RegistrationsPanel` → «Згенерувати сітку» бере всі `status === 'confirmed'` (`BracketPanel.tsx:49`), шафлить їх через `Math.random` (`bracket.ts:113–120`) і будує single_elim з байами або double_elim (лише степінь двійки ≥ 4, `isPowerOfTwo`) → результати кліком по слоту → переможець вирішального матчу автоматично ставить `completed` → подіум і «Статистика перемог» на головній рахуються **за рядком `nickname`** переможця (`HomePage.tsx:71–73`, `participants.ts`). Публічна сторінка турніру ховає список учасників/команд, щойно з'явилась сітка (`TournamentPage.tsx:101`).

Шість фактів, які визначають увесь розділ 4:

1. учасник сітки = рядок `registrations` → згенеровані команди мусять бути такими рядками, інакше сітка/подіум переписуються;
2. адмінської insert-політики на `registrations` немає → після закриття реєстрації команди записує лише RPC;
3. автостворення серії копіює фіксований список колонок → новий режим треба додати туди явно;
4. подіум і статистика ключуються рядком `nickname` → «Команда 1» стала б «гравцем» з перемогами;
5. командність визначається лише через `team_size` → потрібен другий перемикач режиму;
6. публічна сторінка ховає учасників, щойно є сітка → гравець фул-рандому не знайде свою команду.

## 2. Оцінка специфікації

### 2.1 Що в ній добре

- Правильний принцип: рандом на рівні вибору серед **допустимих збалансованих** варіантів, а не «рандом → ручне виправлення» (§18).
- Клас — обмеження, а не бали (§12): сила класу залежить від складу пачки.
- Розуміння, що балансувати лише суму недостатньо (§15) — стек трьох топів проти шести середніх.
- Верифікація скріншотом як anti-fraud, а не як ручний баланс (§22); версіонування правил і seed (§26); «не вважати бали остаточними, зібрати дані, симулювати» (§28).
- Свідомо відкинуті біжутерія/камені/джин — анкета лишається короткою.

Усе це варто зберегти. Проблеми — у числах, у невизначених параметрах і в самому кроці генерації.

### 2.2 Математика шкали не сходиться з власними порогами

Сума максимумів усіх компонентів за таблицями §4–§10 (перевірено скриптом):

| Компонент | Max |
|---|---:|
| Грейд зброї (R9R2) | 45 |
| Заточка зброї (+12) | 25 |
| ПЗ на зброї | 15 |
| Сет броні (Full R9) | 35 |
| Заточка броні (+12) | 30 |
| Спецсети: 8+12+15 без капу / cap 20 | 35 / 20 |
| Трактат (Імператор) | 20 |
| **Разом** | **205 / 190** |

Наслідки:

- §4 обіцяє «максимум 200–250», §14 задає Tier **S = 220+** — **недосяжний ніколи**. Tier **A = 190–219** досягається лише ідеальним гравцем (з капом — рівно 190).
- §2/§6 кажуть, що R9-броні «ні в кого немає». Без неї максимум = 205 − (35 − 22) = **192** без капу і **177** з капом. Тобто з капом жоден реальний гравець не потрапляє ні в S, ні в A — критерій «кількість S/A гравців» (§15, §17) не має на що спиратися.
- Приклади вигадані поза шкалою: §15 — гравці 250/245/230 (> 205), §20 — Assassin 194 (> 192).
- Реальний розподіл за таблицями спеки: «топ» (R9R2 +12, Full R8R +12, ПЗ, усі сети, Імператор) = 177 → B; «сильний» (РЦГД +10, Full R8R +10, ПЗ, ПА, трактат 7) = 111 → C; «середній» (R8R +10, Full R8 +8, ПЗ, Спів, трактат 6) = 87 → D; «Нірвана +5» = 13 → D. Майже весь пул злипається у C/D — Tier не розрізняє нікого.
- Дрібне: §6 у заголовку «максимум 35–40», у таблиці — 35.

**Рекомендація.** Зафіксувати максимум явно (після поправок власника — ПА у грейді зброї, джин — це 200, реалістично 187), перерахувати пороги Tier під цю шкалу (розділ 3.1) і **не використовувати Tier усередині алгоритму взагалі** — лише як бейдж в адмінці (розділ 3.2 пояснює, чим замінити).

### 2.4 Формула штрафу (§17) не працює як записано

`Penalty = GearDiff × 1.0 + TierDiff × 0.7 + ClassPenalty × 2.0 + RoleDiff × 0.5`

- **Різні одиниці.** GearDiff — у балах (десятки–сотні на суму команди ~500–1100), решта — у штуках (0…S). Один дублікат класу коштує 2.0 = **2 бали різниці сум**, тоді як §20 називає 5–10 балів «прийнятною» різницею. Оптимізатор радо «купить» дубль класу за 3 бали балансу — прямо всупереч §12.
- **Суперечність із собою.** §16 крок 3 уже відкидає дублікати класів як hard constraint, а §17 додає їх у м'який штраф — і тут же каже, що вони «повинні бути Hard Constraint».
- **Не визначено для K > 2 команд.** Що таке «різниця», коли команд 8: max−min? попарні? σ?
- **Сума і середнє — один критерій.** При рівному розмірі команд (hard constraint §16) `Average = Total / S`; враховано двічі.
- **Головне з §15 у формулі відсутнє.** Приклад §15 (рівні суми 1070 : 1070, але найсильніший 250 проти 180 — різниця 70) саме про «максимальний Score гравця» — у §17 такого члена немає.
- **Ролі без мапи.** §13 перелічує 5 ролей, але жоден розділ не каже, який клас до якої ролі; список класів теж не наведено (лише в прикладах — з них видно Seeker і Mystic, тобто 10 класів).

### 2.5 Крок «згенерувати 1 000–10 000 випадкових і відфільтрувати» (§16) не дає нічого

- Якщо розподіл справді випадковий (перемішати N і нарізати по S), імовірність, що одна команда з 6 не має двох однакових класів (10 класів по 6, N = 60) = C(10,6)·6⁶ / C(60,6) = 9 797 760 / 50 063 860 ≈ **0,196**. Для 10 команд одночасно ≈ 0,196¹⁰ ≈ 8·10⁻⁸. Серед 10 000 кандидатів очікувано **0,001 допустимого** — крок 3 відкине все.
- Навіть якщо генерувати кандидатів конструктивно (класи дотримано за побудовою), випадкове семплування безнадійне: простір розподілів для N=60, S=6 ≈ 60!/(6!¹⁰·10!) ≈ 10⁴⁷. У прототипі 10 000 конструктивних кандидатів дали розкид сум між командами **74 бали** (N=60) і **124** (N=120) — це 14–24 % суми команди; 100 000 кандидатів за 1,8–3,3 с — усе ще 42/84. Локальний пошук зі свопами дає **4–7 балів за ~0,07–0,6 с** (таблиця в 3.2).
- §18: «знайти 100 найкращих, вибрати з top 10» — 100 ніде не використовується.

### 2.6 Чого спека не визначає, а реалізації треба

| Параметр | Що каже спека | Що потрібно вирішити |
|---|---|---|
| Розмір команди S | приклади по 6, параметра немає | брати з `tournaments.team_size` (у редакторі дефолт 5, дозволено 2…20) |
| Кількість команд K і сітка | не пов'язані | `double_elim` у коді приймає **лише** K = степінь двійки ≥ 4; single_elim — K ≥ 2 з байами. N=23, S=6 → K=3 → double_elim неможливий без 24 гравців |
| Залишок N mod S | «порушено кількість гравців у пачці» = hard constraint, про залишок — нічого | резерв: хто, в якому порядку, як показувати |
| Клас із N_c > K | «дозволити дублювання» як fallback | як саме розподіляти дублі (рівномірно: ⌊N_c/K⌋…⌈N_c/K⌉) |
| Заміни, неявка, пізня заявка | лише «дискваліфікація або наперед визначений штраф» (§22), без правила заміни | правило заміни з резерву; що робити з заявкою після формування |
| Нічиї за штрафом | — | tie-break |
| Seed / PRNG | «використовується random seed» | `Math.random` не сідується; потрібен власний PRNG; **seed + версія правил недостатньо** — результат залежить від точного набору гравців (у прототипі +1 гравець при тому ж seed змінив склад для 60/60 гравців), тож треба зберігати ще й snapshot входу |
| Кількість кандидатів | 1 000/5 000/10 000 «залежно від кількості» | правило не дано; для локального пошуку параметр інший (рестарти × ітерації) |

## 3. Пропозиції покращень

### 3.1 Модель балів `balance-v1.0`

Принципи: (1) кожна опція форми = рівно один рядок таблиці; (2) у кожній категорії є нульовий варіант; (3) максимум зафіксовано — **255** (реалістично 242, поки ні в кого немає R9-броні); (4) усі константи версіоновані: вбудована `balance-v1.0` — у коді (`gearRules.ts`), наступні версії суперадмін зберігає з адмінки («Шкала балів») у таблицю `balance_rules` (міграція 0019); версії незмінні, турнір зберігає версію, за якою рахувався, нові турніри беруть найновішу.

**3.1.1 Грейд зброї — max 45**

Порядок і бали зібрано з відповідей власника (ПА фіксований за грейдом: ЦГД 30, РЦГД 50, R9 30, R9R1 40, R9R2 50; ЦГД сильніша за R8R і за Нірвану). ПА вшито в бали грейду — окремого поля «ПА» немає, подвійного обліку теж. Рідкість на сервері за 8 місяців: ЦГД ~5, РЦГД ~20 (апається з ЦГД), R9 — 1, R9R1 — 2, R9R2 — 2; тому за проханням власника розриви R8R → ЦГД і РЦГД → R9R2 великі (+15), а все між ними — дорожче. Максимум компонента — 60.

| Код | Опція у формі | Бали | Підстава |
|---|---|---:|---|
| `other` | Інше / нижче Нірвани | 0 | нульовий варіант |
| `nirvana` | Нірвана | 5 | бюджет, 0 ПА |
| `r8r` | R8R | 10 | рандом-стати, фіксованого ПА немає; ЦГД сильніша |
| `cgd` | ЦГД | 25 | 30 ПА; ~5 штук на сервері |
| `r9` | R9 | 32 | 30 ПА + вища база, ніж у ЦГД; 1 штука |

### 3.2 Алгоритм формування команд

Замість «10 000 випадкових → фільтр → найкращий» — **конструктивний старт + локальний пошук + випадковий вибір серед майже рівних розв'язків**. Усе працює у браузері адміна, чистий TypeScript-модуль без Supabase/DOM, детермінований за seed.

**Вхід/вихід.** N підтверджених гравців `{id, nickname, cls, role, score}`, розмір команди S, `teamCount` K (дефолт ⌊N/S⌋; для double_elim — найбільша степінь двійки ≥ 4), рядковий `seed`, `rules`. Вихід: K команд по S, впорядкований резерв, `penalty`, snapshot для відтворення.

**Крок 0 — PRNG і канонізація.** PRNG **sfc32**, seed зі строки через **cyrb128** (цілочисельна арифметика — однаково в усіх JS-движках). `Math.random` не використовується. Гравці сортуються за `id` до першого виклику rng — порядок вибірки з БД не впливає. Seed команд — `balance_seed`; посів сітки — окремий `bracket_seed`, який генерується заново при кожному «Решафл сітки» (інакше з фіксованим seed решафл був би no-op); обидва зберігаються в `tournaments`, тож і команди, і сітка відтворювані (§19/§25). Snapshot генерації = `{rulesVersion, algoVersion, seed, teamSize, teamCount, reservePolicy, inputHash, players: [[id, cls, score]…]}` — це частина `BalanceStats` (визначення в 4.3).

**Крок A — конструктивний старт (класи виконуються за побудовою).** Гравці по бакетах за класом; порядок класів — seeded-шафл, потім стабільне сортування за розміром бакета (більші першими, щоб дублі при N_c > K лягали рівномірно); кожен бакет перемішаний; роздача по колу від випадкового зсуву в першу команду, де є місце **і немає цього класу**; fallback (лише коли N_c > K) — перша команда, де є місце. Гарантія: кількість дублів = Σ_c max(0, N_c − K) — теоретичний мінімум (принцип Діріхле), розподіл дублів ⌊N_c/K⌋…⌈N_c/K⌉. Перевірено: 10 сінів на 5 команд → [2,2,2,2,2].

**Крок B — локальний пошук (simulated-annealing-lite).** Ітерація: обрати дві команди й по гравцю в кожній, свопнути; **інваріант класів** — якщо в будь-якій із двох команд кількість дублів зросла, відкат; інакше Δ штрафу (перерахунок лише двох команд, O(S log S)); прийняти, якщо Δ ≤ 0 або `rng() < exp(−Δ/T)`, де T геометрично спадає з 6 до 0,05 балів — саме на цьому варіанті зроблено всі заміри нижче. Тримати best. R рестартів «A → B», результати дедуплікуються за сигнатурою. (Є exp-free варіант — лінійне охолодження і `rng() < 1 − Δ/T`, без `Math.exp`/`Math.pow`, якщо хочеться гарантії біт-у-біт між движками; він трохи гірший: 5,7 / 10,2 бала проти 5,2 / 8,2 у тій самій симуляції. Оскільки результат і так зберігається як snapshot, а не перераховується, дефолт — exp-варіант.)

**Штраф — впорядковані статистики замість Tier.** Для команди t відсортувати score за спаданням, `Top_k(t)` = сума k найсильніших, `range(x) = max_t x − min_t x`:

```
penalty =  1.0 · range(Total)                       // різниця сум
         + std_t(Total)                              // рівномірність по всіх K (tie-break)
         + Σ_{k=1}^{S−1} (1/k) · range(Top_k)        // «профіль сили»: top-1, top-2, …
         + 3 · Σ_r max(0, range(roleCount_r) − slack_r)   // м'який баланс ролей
         + 1000 · max(0, dups − unavoidableDups)     // guard, за побудовою завжди 0
```

Усі члени — в балах score, без порогів. Приклад §15 (суми рівні 1070 : 1070): префікси A = 250/495/725/845/960/1070, B = 180/360/540/720/900/1070 → діапазони 70/135/185/125/60/0 з вагами 1, ½, ⅓, ¼, ⅕, 1 → **штраф 242,4** при штрафі «лише сума» = 0. Локальний пошук на тих самих 12 гравцях знаходить 245/180/180/180/170/120 vs 250/230/180/180/115/110 зі штрафом 79,6 — трійку 250/245/230 неминуче ділити 2:1, це нижня межа. `range(Top_1)` має нижню межу = score(1-й) − score(K-й) популяції; алгоритм її досягає.

**Вибір і reroll.** Кандидати = різні розв'язки зі штрафом ≤ best + ε (ε = 5 балів ≈ 1 % суми команди — збігається з «5–10 балів прийнятно» §20), не більше 10; вибір рівномірно тим самим seeded rng. Той самий snapshot + seed → той самий результат (перевірено); новий seed = «Перегенерувати»; зміна набору гравців — інша жеребка навіть із тим самим seed (UI має це прямо казати).

**Виміряно у прототипі** (Node 20, S = 6, 10 класів, синтетичні score за таблицями спеки, медіана ≈ 83, сума команди ≈ 510):

| Конфігурація | N=60 (K=10) | N=120 (K=20) | Розкид сум команд, балів |
|---|---:|---:|---|
| spec: random × 10 000 | 175 мс | 307 мс | 74 / 124 |
| spec: random × 100 000 | 1 814 мс | 3 313 мс | 42 / 84 |
| локальний пошук 1 × 2 000 | 10 мс | 9 мс | 16 / 29 |
| локальний пошук 1 × 20 000 | 69 мс | 76 мс | 4 / 6 |
| **8 × 20 000 (дефолт)** | **513 мс** | **598 мс** | 6 / 6 |

За 100 різними seed при 8 × 20 000: розкид сум у середньому 5,2 (макс 11) для N=60 і 8,2 (макс 15) для N=120 — 1–2 % суми команди; розкид найсильнішого гравця у середньому на теоретичній межі (34,0 при межі 34; 38,3 при межі 38; макс 38 / 41). Один аномальний гравець (190 при максимумі ~146) не ламає баланс сум (розкид 4). Прогін повторено незалежно — показники якості збіглися один в один (seed-детермінізм), час на іншій машині 0,6–0,8 с. Дефолт: 8 рестартів × 20 000 ітерацій, для N > 150 — `iterations = 200·N`; до секунди блокування кнопки прийнятно (модуль чистий — за бажання в Web Worker).

**Крайові випадки.**

| Випадок | Правило |
|---|---|
| ⌊N/S⌋ < 2 | помилка до пошуку: «Потрібно щонайменше 2·S підтверджених гравців» |
| N mod S ≠ 0 | резерв; політика `latest` (дефолт: останні за `created_at` — прозоре правило, яке легко пояснити) / `random` (seeded хвіст) / `manual` (адмін закріплює). Порядок у резерві = порядок заміни |
| double_elim | адмін задає K (UI підказує найближчу степінь двійки ≥ 4), решта в резерв |
| N_c > K | дублі неминучі, розкладаються рівномірно; попередження в UI: «Жерців 5 на 4 команди — дублювання неминуче» |
| усі score рівні | penalty 0 всюди, вибір суто випадковий, класи все одно унікальні |
| пізня заявка після формування | до публікації — перегенерація (новий seed, новий snapshot); після — гравець у резерв, вставка вручну; перегенерація можлива, поки в сітці немає результатів (сітка видаляється з підтвердженням), з результатами — лише заміна |
| неявка | `suggestReplacement`: з резерву спочатку той самий клас → клас, якого нема в команді → будь-який; далі за |Δscore|; адмін підтверджує; seed/snapshot не змінюються, у `substitutions[]` пишеться заміна |
| заявка без анкети (стара) | не допускається до генерації; дозаповнити або відхилити |

**Симуляція і тести** (`vitest`, `src/data/__tests__/balance.test.ts` + `scripts/simulate-balance.ts`): генератор синтетичних популяцій (5–10 профілів: «топовий сервер», «змішаний», «слабкий», «30 % сінів»), N ∈ {24, 36, 60, 120}, 200–1 000 seed з бюджетом 1 × 20 000 (≈70 мс → 10 000 прогонів ≈ 12 хв; повний 8 × 20 000 — окремий smoke на 20 seed, бо 10 000 прогонів = 1,5 год). Метрики та пороги прийняття: розкид сум mean ≤ 2 % / max ≤ 4 % суми команди; `range(Top_1)` ≤ нижня межа + 5; `Top_2/Top_3` ≤ межа + 10; дублів понад неминучі = 0; для N_c > K розкид по командах ≤ 1; концентрація «≥2 з top-3 в одній команді» ≤ 5 % (метрика через top-K непридатна: K-й і K+1-й гравці відрізняються на 1–2 бали, у прототипі 38 %/81 % — артефакт межі); детермінізм 100 %; runtime N=120 ≤ 1,5 с. Юніт-тести: guard K<2, кожна політика резерву, N_c > K, всі score рівні, приклад §15 → 242,4, порядок кандидатів `suggestReplacement`, зміна одного гравця змінює `inputHash`.

```ts
export function formTeams(input, opts) {
  const { teamSize: S, seed, rules } = opts;
  const R = opts.restarts ?? 8, I = opts.iterations ?? Math.max(20000, 200 * input.length);
  const rng = createRng(seed + ':teams');
  const players = input.slice().sort((a, b) => (a.id < b.id ? -1 : 1));   // канонічний порядок
  const K = opts.teamCount ?? Math.floor(players.length / S);
  if (K < 2 || K * S > players.length) throw new Error(`Потрібно щонайменше ${2 * S} гравців (зараз ${players.length}).`);
  const { active, reserve } = splitReserve(players, K * S, opts, rng);
  const unav = unavoidable(active, K);
  const sols = new Map();
  for (let r = 0; r < R; r++) {
    const res = localSearch(constructiveDeal(active, K, S, rng), S, unav, rules, rng, I);
    const sig = signature(res.teams);
    if (!sols.has(sig) || sols.get(sig).penalty > res.penalty) sols.set(sig, res);
  }
  const list = [...sols.values()].sort((a, b) => a.penalty - b.penalty);
  const cands = list.filter((s) => s.penalty <= list[0].penalty + rules.epsilon).slice(0, rules.topN);
  const chosen = cands[Math.floor(rng() * cands.length)];
  return { teams: chosen.teams, reserve, penalty: chosen.penalty, bestPenalty: list[0].penalty,
           candidates: cands.length, distinct: list.length, snapshot: makeSnapshot(players, opts, K) };
}

function localSearch(teams, S, unav, rules, rng, I) {
  const K = teams.length, stats = teams.map(teamStats);
  let cur = penalty(stats, S, unav, rules.weights), best = cur, bestTeams = clone(teams);
  for (let it = 0; it < I; it++) {
    const T = rules.T0 * Math.pow(rules.T1 / rules.T0, it / I);           // геометричне охолодження (варіант замірів)
    const a = Math.floor(rng() * K); let b = Math.floor(rng() * (K - 1)); if (b >= a) b++;
    const i = Math.floor(rng() * S), j = Math.floor(rng() * S);
    const pa = teams[a][i], pb = teams[b][j];
    if (pa.cls === pb.cls && pa.score === pb.score) continue;
    teams[a][i] = pb; teams[b][j] = pa;
    const sa = teamStats(teams[a]), sb = teamStats(teams[b]);
    if (sa.dup > stats[a].dup || sb.dup > stats[b].dup) { teams[a][i] = pa; teams[b][j] = pb; continue; } // інваріант класів
    const oa = stats[a], ob = stats[b]; stats[a] = sa; stats[b] = sb;
    const next = penalty(stats, S, unav, rules.weights), d = next - cur;
    if (d <= 0 || rng() < Math.exp(-d / T)) { cur = next; if (cur < best) { best = cur; bestTeams = clone(teams); } }
    else { teams[a][i] = pa; teams[b][j] = pb; stats[a] = oa; stats[b] = ob; }
  }
  return { teams: bestTeams, penalty: best };
}
```

Параметри за замовчуванням: `restarts 8`, `iterations max(20000, 200·N)`, `T0/T1 = 6/0.05`, ваги `total 1, top 1, role 3, dup 1000`, `slack_r = (n_r mod K == 0) ? 0 : 1` (n_r — гравців ролі r серед активних; нерівний поділ на 1 не штрафується), `roleOf` — таблиця з 3.4 (прототип `sim.mjs` має `blademaster: 'tank'` — вирівняти при переносі), `epsilon 5`, `topN 10`, `reservePolicy latest`, `ALGO_VERSION 'teams-ls-v1'` (будь-яка зміна кроків/штрафу → нова версія), `rulesVersion 'balance-v1.0'`. Усе це — `RULES[version].balance` (4.3).

### 3.3 UX

**Назва режиму.** Три варіанти: «Балансний фул-рандом» (сленг спільноти + одразу відповідає на заперечення «рандом = дисбаланс»; майже дослівно §23), «Випадкові збалансовані команди» (зрозуміло без сленгу, довго для бейджів), «Рандомні пачки» (коротко, але звучить як «рандомайзер», проти чого застерігає §23). **Рекомендація: «Балансний фул-рандом»**, коротка форма «фул-рандом», довга форма — у підказках.

**Редактор турніру.** Не окремий чекбокс (він мав би сенс лише при командному турнірі, і два способи формування взаємовиключні), а `select` «Формування команд» в одному `.field-row` з «Кількість людей в команді», видимий лише при увімкненому «Командний турнір»:

```

  Кількість людей в команді [ 5 ]   Формування команд [ Готові команди ▾ ]

Дефолт «Готові команди» — існуючі серії не змінюють поведінки. Якщо в турнірі вже є заявки — select і розмір команди `disabled` (патерн «Матч за 3-тє місце» при double_elim) з підказкою «Режим і розмір команди не змінюються — вже є заявки (12)»; редактору для цього потрібен один `fetchRegistrations(initial.id)` при відкритті. Для фул-рандом + double_elim — підказка під «Тип сітки»: «кількість команд обираєш під час формування — степінь двійки, зайві гравці в резерв». Кнопка «Вставити стандартні правила (фул-рандом 5х5)» — секція нижче.

**Форма заявки (гілка фул-рандому) — компактна, без «конструктора».** Один нік + анкета з 7 select-ів і 4 чекбоксів, на один екран десктопа; без скріншотів і без довгих пояснень. Поточна гілка «назва команди + N ніків» лишається для «Готових команд». Порядок:

*Панель заявок* у цьому режимі: смужка лічильників «Підтверджено 23 · Очікують 4 · Команд по 5: 4 (+3 у резерві) · Класи: Жрець 5 · Воїн 4 · …» (+ `badge warn` «Жерців 5 на 4 команди — дублювання неминуче»); у рядку — клас, компактний гір (`R9R2 +12 · R8R +8 · ПЗ-сет · Тракт 8 · джин 100/100`), **гір-скор + tier** (`badge warn` для S/A, `mute` для решти), статус, дії як зараз + **«✎» редагування анкети** (спільний компонент `GearFields` з формою гравця). Це і є інструмент верифікації без скріншотів: адмін перевірив у грі → виправив грейд → скор перерахувався; без нього єдина реакція на чесну помилку — відхилити заявку. Після формування команд «Відхилити/✕» блокуються з підказкою «Спершу переформуй команди».

*Блок «Команди»* (новий `TeamsPanel` між заявками й сіткою, лише для цього режиму) — чотири стани: (A) реєстрація відкрита → «Команди формуються після закриття реєстрації» + кнопка «Закрити реєстрацію» (статус — вільний select, тож гейтинг робимо власною перевіркою `effectiveStatus ∈ {registration_closed, in_progress}`); (B) закрито, команд немає → лічильники + «Сформувати команди» (`disabled` при N < 2·S); (C) команди затверджені, результатів немає → картки команд + «Резерв» + мета-рядок «seed a1b2c3 · balance-v1.0 · сформовано 08.09 20:14 · замін: 1» + «Переформувати» (якщо сітка вже є, але без результатів — `confirm`, і RPC викликається з `p_drop_bracket = true`: він сам атомарно видаляє сітку й перезаписує команди) + «Розформувати»; (D) є результати → усе read-only, лише «✎ Замінити» на гравцях (окремий RPC `substitute_team_member`, працює і при наявній сітці).

*Модалка «Формування команд»* (базовий `.modal` у `styles.css` має `width: min(720px, 100%)` — тут inline `style={{ width: 'min(1000px, 100%)' }}` за прикладом `TournamentEditor`; картки команд у `grid-template-columns: repeat(auto-fill, minmax(260px, 1fr))`, на телефоні — один стовпчик, своп двома тапами): поле «Команд» (дефолт ⌊N/S⌋, для double_elim — степінь двійки), seed read-only + «🎲 Перегенерувати», смужка балансу («Сума гіру 903–911 · розкид 8», «Дублікати класів 0», «S+A по командах 2·2·1·2», penalty), картки команд з `input` назви (дефолт «Команда 1…K», можна перейменувати) і рядками гравців, **ручний своп двома кліками** (перший — підсвітити, другий — обміняти, Esc — скасувати; DnD-бібліотеки в проєкті немає, нативний HTML5 DnD не працює на тачі), картка «Резерв», футер «Скасувати / Затвердити команди». Після затвердження realtime-підписка оновлює публічну сторінку.

*Панель сітки*: лічильник «Команд: 4 (гравців у командах 20, у резерві 3)»; «Згенерувати сітку» лише після затвердження команд; «Решафл» → «Решафл сітки» (не плутати з «Переформувати»; міняє лише посів, §19).

*Заміна гравця* (неявка/дискваліфікація): «✎ Замінити» → кандидати з резерву, той самий клас першим, `.hint` «сума команди стане 899 (−8)»; «Прибрати без заміни» — команда грає неповним складом; сітка не чіпається (id команди стабільний). Запис — RPC `substitute_team_member` (4.2): вибулий отримує `status = 'rejected'` (в UI — «вибув»), щоб не потрапити в наступне переформування, `team_registration_id` переписується, `member_nicknames` команди оновлюється, у `balance_stats.substitutions` додається запис; «Прибрати без заміни» — той самий RPC без `p_in_id`.

**Публічна сторінка.** Під статусом — «Формат: балансний фул-рандом · команди по 5 · команду формує система випадково після закриття реєстрації». До формування — «Учасники (23)» чіпами «Nick · Жрець» і рядок «Класи: Жрець 5 · …» (видно, кого бракує). Після — картки команд: назва · «сумарний гір 907» · чіпи «Nick · Клас» · згорнутий `<details>` «Заявлене спорядження» (по рядку на гравця) + картка «Резерв» + рядок довіри «Розкид сумарного гіру між командами: 8 балів · seed a1b2c3 · balance-v1.0». **Після генерації сітки блок команд не ховати** (зараз ховається — гравець не знайде свою команду, а в сітці лише назва): під сіткою `<details className="card" open>` «Склади команд», у `BracketView` — `title` на слоті зі списком ніків.

| Дані | Публічно | Адміну | Чому |
|---|---|---|---|
| нік, клас | так | так | базова інформація |
| відповіді анкети | так, у `<details>` | так | і так видно при огляді персонажа; «народна» верифікація і стримувач заниження |
| сума гіру команди, розкид, seed | так | так | доводить, що баланс реальний, без ранжування людей |
| персональний гір-скор | ні | так | число без контексту породжує суперечки |
| персональний tier | ні | так | межі попередні; публічна «D» — стигма |

**Пресет правил** (нова секція `RULE_SECTIONS` «Балансний фул-рандом (командний)», `standardRulesFor(teamSize, mode)`): ти не обираєш команду; реєстрація індивідуальна, один персонаж — одна заявка; анкета чесна, адмін перевіряє спорядження в грі; розбіжність — дискваліфікація, місце займає резерв; ПЗ-сет / ПА-сет / Спів-Аспід рахуються від порогів 30 ПЗ / 30 ПА / 3.33 уд/с / −30 % (без бафів); склади публікуються і не міняються на прохання; резерв — останні за часом реєстрації; неявка — заміна з резерву, без резерву команда грає неповним складом; трактат — в анкеті вказується найкращий, який береш на турнір, свап униз дозволений, угору — ні (свап у бою можливий, «вдягнений» — не величина); бойові обмеження — як для формату KхK.

Позначки лишилися лише там, де факт досі не перевірений: **[?]**.

**Ростер і ролі.** 1.4.6 = 5 рас / 10 класів. У RU-локалізації **«Шаман» = Psychic** (Амфібії, магічний ДД), а **«Містик» = Mystic** (Древні, хіл + саммони) — підтверджено власником; саме тому правило 2х2 «Містик + Прист» забороняє двох хілерів. У БД — англійський ключ, у select — **лише українські** підписи (рішення власника; «Танк», а не «Оборотень»); словник підписів — одне місце в `gearRules.ts`, за потреби «Прист» ↔ «Жрець» чи «Сін» ↔ «Убивця» міняється одним рядком:

| Ключ | Підпис у select | Роль (soft) | Гібрид |
|---|---|---|---|
| `blademaster` | Воїн | Melee DPS | frontline, AoE-контроль |
| `wizard` | Маг | Ranged DPS | трохи контролю |
| `cleric` | Прист | Support | може бути маг-ДД |
| `archer` | Лучник | Ranged DPS | аспд-білд |
| `barbarian` | Танк | Tank / Frontline | у ПвП часто фіст-барб (melee) |
| `venomancer` | Друїд | Control / Utility | ranged-DPS-гібрид |
| `assassin` | Сін | Melee DPS | контроль станами |
| `psychic` | Шаман | Ranged DPS | Control (вуду, soulburn) |
| `seeker` | Страж | Melee DPS | дебафи, частина скілів дистанційна |
| `mystic` | Містик | Support | може ДД |

Мапа ролей — м'який штраф (3.2), а не правило: штрафується лише нерівномірний розподіл ролі **між командами** понад slack; абсолютних меж на пачку («≥ 1 Support у кожній», «≤ 3 Melee») v1.0 не накладає — кандидат у v1.1, якщо реальні жеребки покажуть потребу. Мапа живе в `RULES[version].balance.roleOf` і правиться без коду; прототип `sim.mjs` має `blademaster: 'tank'` — вирівняти під цю таблицю при переносі.

**ПА/ПЗ — центральна механіка цієї версії.** ПА = показник атаки, ПЗ = показник захисту; `урон = X · 0.99^(ПЗ_цілі − ПА_атакуючого)` — приблизно 1 % за пункт. За власником: лінійка зброї має **фіксований ПА** — ЦГД 30, РЦГД 50, R9 30, R9R1 40, R9R2 50 — він вшитий у бали грейду (3.1.1); окремо існує **ПЗ-зброя** з показником захисту — це чекбокс 3.1.3, доступний лише поза лінійкою з ПА. Решта ПА/ПЗ на сервері приходить з бонусів сетів (Нірвана-2: ПА+5/ПЗ+13; R9: сет ПЗ+20), каменів (1 ПА або 2 ПЗ за камінь) і біжутерії. Ця частина — найбільша дірка спеки: 4×4 слоти броні + біжутерія + бонуси легко дають 30–50 ПЗ або 15–25 ПА, того ж порядку, що різниця між грейдами зброї; «Full R8R +10» без каменів і з фул-ПЗ-каменями отримали б однаковий score. Компроміс, узгоджений з власником: два необов'язкові числа з вікна персонажа без бафів — «Показник атаки» і «Показник захисту» — **збираються, але у v1.0 не рахуються** (колонки `attack_level`, `defense_level`; у формі — згорнутий блок). Після першого турніру подивитись на кореляцію зі score і в `balance-v1.1` або замінити ними «ПЗ-сет / ПА-сет», або додати смугами (0–10 → 0 · 11–30 → 5 · 31–50 → 10 · 51–70 → 15 · 71+ → 20 для кожного).

**Лінійки предметів** (підтверджено власником): ЦГД сильніша за R8R і за Нірвану; РЦГД — перековка ЦГД з 50 ПА; на сервері є R9R1 (40 ПА) як проміжний крок до R9R2. R8R — рандом-стати без фіксованого ПА, звідси 10 балів. Броня: Нірвана — бюджет, «Нірвана / R8» — трохи краще за Нірвану, але гірше за R8, далі R8 < R8R — як у спеці. R8R2 та поділ Нірвани на 1/2 грейд власник не згадував — у v1.0 їх немає [?]. R9-броню в select не показувати, поки ні в кого немає (feature flag, категорія лишається у версії правил).

**Спецсети.** «ПА-сет / ПЗ-сет» — свап-комплекти броні+біжутерії на показник атаки/захисту; «Спів/Аспід» — комплект на −час активації (кастери, RU «пение») або −пауза між атаками (фізики). Одночасно активний один — звідси формула 3.1.6. Пороги узгоджено: ПЗ-сет = сумарний ПЗ ≥ 30 у комплекті без бафів; ПА-сет = ПА ≥ 30; Аспід = ≥ 3.33 уд/с без бафів; Спів = ≥ −30 % часу активації з предметів.

**Трактати.** За рівнями: Бог Пань Гу — 6-й; Глас полуночи / Юболо / Душа моря — 7-й; Гегемонія — 8-й; Імператор — 9-й; вище — «Несравненный». Власник підтвердив: «Гео» = Гегемонія. Свап трактата в бою можливий (підтверджено) → правило «найкращий, який візьмеш; свап униз дозволений, угору — ні».

**Джин.** За власником — враховуємо двома значеннями: «100/100» (топ) і «100−»; бали в 3.1.8.

**Що ще спека не враховує** (за ризиком): сумарні ПА/ПЗ з каменів/біжі (високий — закривається двома числами вище, коли їх почнемо рахувати); Нірвана-1 vs 2 (середній, не розділяємо, поки власник не скаже, що є обидві); ступінь аспд 3.33 vs 5.0 (низько-середній); якість ролу R8R (низький — ігнорувати). Морайський шмот працює лише проти монстрів — ігнорувати.

**Верифікація без скріншотів** (рішення власника): адмін знає сервер і перевіряє спорядження в грі за потреби; відповіді анкети видно публічно на сторінці турніру — спільнота сама помітить занижений гір; чесна помилка виправляється кнопкою «✎» в адмінці, неправда — дискваліфікація і заміна з резерву. Колонок `screenshot_url` / `gear_verified` у схемі немає.

## 4. Як це лягає в кодову базу

### 4.1 Представлення команд: синтетичні рядки `registrations`

| | **A. Команди = рядки `registrations` (`kind='team'`)** | B. Таблиця `tournament_teams` + зміна FK |
|---|---|---|
| Сітка (`bracket_matches.*_id` → `registrations.id`) | без змін | поліморфний FK або друга трійка колонок; правки `generate*`, `setMatchWinner`, `fetchPodium`, `fetchChampion` |
| Імена (`BracketView.nameFor`, `TournamentPage`, `Podium`, `HomePage`) | без змін — `nickname` = назва команди | всі споживачі резолвлять два джерела |
| Автозавершення, решафл, `bracketHasResults` | без змін | FK-каскади переписати |
| Realtime (0003) | без змін | нова таблиця в publication + підписка |
| RLS | один RPC | таблиця + політики + RPC |
| Ризики | спільний простір імен з ніками (індекс по `kind`); статистика за nickname (фільтр по `kind`) | великий рефакторинг без користі для фічі |

**Обираємо A.** Гравець — `kind='player'` з анкетою і FK `team_registration_id` на свою команду; команда — `kind='team'`, `status='confirmed'`, `member_nicknames` заповнено (кеш для існуючого UI). Усі старі рядки лишаються `kind='player'` (у тому числі «заявка = готова команда» у fixed-режимі).

**Gear score не зберігається — рахується на читанні.** Публічна insert-політика перевіряє лише турнір, а не значення колонок: анонім через REST може вставити довільний `gear_score` (зараз може навіть `status='confirmed'`). Тому в БД — лише дискретні відповіді з check-констрейнтами; `computeGearScore(gear, rulesVersion)` у `src/data/gearRules.ts` тримає всі версії таблиць; турнір фіксує `balance_rules_version`; знімок score кожного гравця на момент генерації — у `tournaments.balance_stats` (аудит + відтворюваність без перерахунку за новими правилами).

-- p_teams: [{"name":"Команда 1","member_ids":["<uuid>",…]},…]; '[]' = розформувати.
-- p_drop_bracket = true: якщо сітка вже є, але без жодного результату — видалити її в тій самій транзакції.
create or replace function apply_balanced_teams(
  p_tournament_id uuid, p_seed text, p_rules_version text, p_stats jsonb, p_teams jsonb,
  p_drop_bracket boolean default false
) returns void
language plpgsql security definer set search_path = public as $$
declare
  t tournaments%rowtype; team jsonb; member_ids uuid[]; all_ids uuid[] := '{}'; new_team_id uuid;
begin
  select * into t from tournaments where id = p_tournament_id;
  if not found then raise exception 'Турнір не знайдено'; end if;
  if not (is_superadmin() or t.created_by = auth.uid()) then raise exception 'Немає прав на цей турнір'; end if;
  if t.team_mode <> 'balanced_random' or t.team_size is null then raise exception 'Турнір не в режимі балансного фул-рандому'; end if;
  if exists (select 1 from bracket_matches where tournament_id = p_tournament_id) then
    if exists (select 1 from bracket_matches where tournament_id = p_tournament_id
               and winner_id is not null and participant1_id is not null and participant2_id is not null) then
      raise exception 'У сітці вже є результати — переформування заборонено, лише заміни';
    end if;
    if not p_drop_bracket then
      raise exception 'Сітку вже згенеровано — переформування видалить її (потрібне підтвердження)';
    end if;
    delete from bracket_matches where tournament_id = p_tournament_id;
    update tournaments set bracket_size = null where id = p_tournament_id;
  end if;

  update registrations set team_registration_id = null where tournament_id = p_tournament_id and kind = 'player';
  delete from registrations where tournament_id = p_tournament_id and kind = 'team';

  for team in select * from jsonb_array_elements(coalesce(p_teams, '[]'::jsonb)) loop
    select coalesce(array_agg(x::uuid), '{}') into member_ids from jsonb_array_elements_text(team->'member_ids') x;
    if coalesce(array_length(member_ids, 1), 0) <> t.team_size then
      raise exception 'Команда «%»: % гравців замість %', team->>'name', coalesce(array_length(member_ids, 1), 0), t.team_size;
    end if;
    if exists (select 1 from unnest(member_ids) mid
               where not exists (select 1 from registrations r where r.id = mid and r.tournament_id = p_tournament_id
                                   and r.kind = 'player' and r.status = 'confirmed')) then
      raise exception 'Команда «%» містить непідтвердженого або чужого гравця', team->>'name';
    end if;
    all_ids := all_ids || member_ids;
    insert into registrations (tournament_id, nickname, rules_ack, status, kind, member_nicknames)
    values (p_tournament_id, team->>'name', true, 'confirmed', 'team',
            (select array_agg(r.nickname order by array_position(member_ids, r.id)) from registrations r where r.id = any(member_ids)))
    returning id into new_team_id;
    update registrations set team_registration_id = new_team_id where id = any(member_ids);
  end loop;

  if (select count(*) from unnest(all_ids)) <> (select count(distinct x) from unnest(all_ids) x) then
    raise exception 'Гравець потрапив у дві команди';
  end if;

  update tournaments set balance_seed = p_seed, balance_rules_version = p_rules_version, balance_stats = p_stats, updated_at = now()
  where id = p_tournament_id;
end;
$$;

-- щоб не потрапити в наступне переформування; факт заміни пишеться в balance_stats.substitutions.
create or replace function substitute_team_member(
  p_team_id uuid, p_out_id uuid, p_in_id uuid default null, p_reason text default 'no_show'
) returns void
language plpgsql security definer set search_path = public as $$
declare team registrations%rowtype; t tournaments%rowtype;
begin
  select * into team from registrations where id = p_team_id and kind = 'team';
  if not found then raise exception 'Команду не знайдено'; end if;
  select * into t from tournaments where id = team.tournament_id;
  if not (is_superadmin() or t.created_by = auth.uid()) then raise exception 'Немає прав на цей турнір'; end if;
  if not exists (select 1 from registrations where id = p_out_id and team_registration_id = p_team_id) then
    raise exception 'Гравець не в цій команді';
  end if;
  update registrations set team_registration_id = null, status = 'rejected' where id = p_out_id;
  if p_in_id is not null then
    if not exists (select 1 from registrations r where r.id = p_in_id and r.tournament_id = t.id
                   and r.kind = 'player' and r.status = 'confirmed' and r.team_registration_id is null) then
      raise exception 'Заміна має бути підтвердженим гравцем цього турніру поза командами';
    end if;
    update registrations set team_registration_id = p_team_id where id = p_in_id;
  end if;
  update registrations
  set member_nicknames = (select array_agg(nickname order by created_at) from registrations where team_registration_id = p_team_id)
  where id = p_team_id;
  update tournaments
  set balance_stats = coalesce(balance_stats, '{}'::jsonb) || jsonb_build_object('substitutions',
        coalesce(balance_stats->'substitutions', '[]'::jsonb)
        || jsonb_build_object('teamId', p_team_id, 'out', p_out_id, 'in', p_in_id, 'reason', p_reason, 'at', now())),
      updated_at = now()
  where id = t.id;
end;
$$;

$$;
```

Чому RPC, а не insert-політика для адміна: формування відбувається після закриття реєстрації, коли `registrations_insert_public` уже не пропускає; і це 4 записи (обнулити FK, видалити старі team-рядки, вставити нові, оновити турнір), які мають бути атомарними. Патерн — той самий, що `admin_add_gm` (0007). Lock — на сервері, у два рівні: якщо в сітці є хоч один зафіксований результат двостороннього матчу — переформування заборонене (та сама умова, що в `bracketHasResults`); якщо сітка є без результатів — лише з явним `p_drop_bracket = true`, і тоді RPC сам видаляє її в тій самій транзакції (інакше видалення team-рядків обнулило б `bracket_matches.*_id` через `on delete set null`, а два окремі виклики могли б лишити турнір без сітки при збої другого). `balance_*` у серію **не** копіюються — це результат конкретного турніру. Realtime — без змін: нових таблиць немає, `tournaments` і `registrations` уже в publication (0003) і в `subscribeToTournamentChanges`.

### 4.5 Що може регреснути — чекліст перед мерджем

1. **Unique-індекс** перебудовано під тим самим іменем → повідомлення про дубль у `RegisterPage` працює; два player-рядки з однаковим ніком у турнірі досі відхиляються.
2. **Публічна insert-політика** стала суворішою (`status='pending'`, `kind='player'`): клієнт цих полів не шле — перевірити реєстрацію на соло- і fixed-турніри.
3. **`isBracketParticipant`** для соло/fixed = `confirmed && kind==='player'`; усі старі рядки мають `kind='player'` (default) → поведінка незмінна.
4. **Автостворення серії** переписано: після міграції виконати `select create_due_series_tournaments()` на тестовій серії — `team_mode` і `bracket_new_look` копіюються.
5. **ParticipantsManager / перейменування**: team-рядки не показуються; `renameParticipant` оновлює нік у player-рядках і робить `array_replace` у `member_nicknames` team-рядків; подіум і статистика беруть склад з player-рядків за `team_registration_id` — інакше перейменований гравець мовчки втратив би перемоги у фул-рандомах, а об'єднання ніків розщепило б статистику.
6. **HomePage/подіум**: fixed-команди — як зараз (кредит на назву команди); фул-рандом — кредит кожному члену. `Podium.tsx`/`ChampionBlock` показують назву команди (+ склад).
7. **Видалення/відхилення гравця після формування** блокується в UI; в БД FK `on delete set null` не дасть «висячого» посилання, але команда стане неповною — `TeamsPanel` показує «Неповних команд: 1».
8. **Cron 0016** і `isRegistrationOpen` — не торкаємось.
9. Перед пушем: `npx tsc --noEmit -p tsconfig.json` і `npx vitest run` — у CI цих кроків зараз немає, варто додати.

## 5. Рішення власника і що ще лишилось

**Ігрові факти — відповіді власника (зафіксовано у 3.1 і 3.4)**
1. ПЗ на зброї = показник захисту на **запасній** ПЗ-зброї для свапу (є в будь-кого незалежно від основної); лінійка ЦГД / РЦГД / R9 / R9R1 / R9R2 має фіксований ПА 30 / 50 / 30 / 40 / 50 → ПА вшито в грейд, ПЗ-зброя — окремий чекбокс, завжди видимий.
2. ЦГД сильніша за R8R і за Нірвану → порядок грейдів 3.1.1.
3. Броня: Нірвана — бюджет, далі мікс Нірвани з R8R (14), далі R8R (22); чистий R8 прибрано після відгуку гільдії.
4. Класи: «Шаман» = Psychic, «Містик» = Mystic; Barbarian = «Танк»; підписи лише українською.
5. ПА/ПЗ з вікна персонажа — збирати (не рахувати у v1.0).
6. Пороги спецсетів (30 ПЗ / 30 ПА / 3.33 уд/с / −30 %) — прийнятні.
7. «Гео» = Гегемонія → трактати за рівнем.
8. Свап у бою можливий → правило «найкращий, свап лише вниз».
9. Заточка на сервері доступна → більшість на +10…+12, перекалібрувати після даних.
10. «Заточка броні» = круг точки (броня + біжа + кільця).
11. Джин враховується двома значеннями: «100/100» / «100−».
12. Скріншотів немає.

**Мої прочитання, які варто підтвердити одним словом**
13. РЦГД (35) вище за R9R1 (33) — чи навпаки? *(3.1.1)*
14. ~~ПЗ-зброя буває лише поза лінійкою ЦГД/R9?~~ — відповідь: це запасна зброя для свапу, чекбокс завжди доступний (зроблено).
15. Трактати суворо за рівнем: Пань Гу = 6-й = 5 балів, а не 10 як у спеці? *(3.1.7)*
16. Вага джина 10 з 200 — достатньо? *(3.1.8)*

**Правила турніру — дефолти без заперечень**
17. Резерв при N mod S ≠ 0 — останні за часом реєстрації; адмін може змінити.
18. Публічно — відповіді анкети і сума гіру команди; персональний скор і tier — лише адміну.
19. Неправдива анкета — дискваліфікація + заміна з резерву; чесна помилка — «✎» адміна.
20. Адмін може перейменовувати команди (дефолт «Команда N»).
21. Два Support в одній пачці допустимі (штрафується лише нерівномірність між командами).

**Технічні — дефолти**
22. Розмір команди — поле `team_size` (дефолт редактора 5).
23. Сітка для фул-рандому — single_elim (double_elim лише при 4/8/16 командах).
24. Посів сітки — окремий `bracket_seed`, новий при кожному решафлі.
25. Додати `vitest` + `typecheck` у CI.
